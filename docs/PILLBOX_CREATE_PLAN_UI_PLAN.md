# Pillbox Create Plan UI Plan

## Goal

Привести экран создания плана в таблетнице к более понятной модели:

- отдельно определить, `для кого` создаётся план
- отдельно определить, `кому` приходят уведомления
- убрать путаницу, когда в названии плана написан один человек, а push отправляется другому

На первом этапе делать только фронтенд-изменения, без смены API и backend contract.

## Current Problem

Сейчас на экране создания плана пользователь:

- добавляет лекарства
- вручную вводит название плана
- отдельно выбирает получателей уведомлений

Из-за этого возникает двусмысленность:

- название плана выглядит как адресат плана
- но фактически это просто свободный текст
- `memberAccountIds` в данных означают получателей push, а не того, `для кого` план создан

В результате пользователь может:

- написать `Для бабушки`
- выбрать уведомления для мамы
- получить план с разъехавшимся смыслом

## Product Decision

На экране создания плана `Название плана` должно стать smart field.

Поведение smart field:

- tap по полю открывает bottom sheet
- в sheet можно выбрать одного семейного участника
- в sheet также должен быть fallback-сценарий `Ввести вручную`

Если пользователь выбирает участника семьи:

- поле названия заполняется автоматически
- title собирается из `роль + имя`
- уведомления по умолчанию ставятся на этого же участника

Если пользователь выбирает ручной ввод:

- открывается обычный текстовый ввод
- уведомления не меняются автоматически

Блок `Кому приходят уведомления` остаётся отдельным и редактируемым.

## UX Rules

### 1. Smart title field

На месте обычного input сделать поле выбора с двумя сценариями:

- выбрать человека из семьи
- ввести своё название вручную

Поле должно поддерживать состояния:

- empty: `Выберите, для кого план`
- member-selected: автогенерированное название
- manual: пользовательский текст

### 2. Title generation

Автогенерация названия:

- если есть роль и имя: `Для мамы Саши`, `Для няни Инны`
- если есть только роль: `Для мамы`
- если есть только имя: `Для Инны`

Важно:

- использовать уже существующие данные карточек участников
- не заставлять пользователя вручную писать очевидный title

### 3. Notification defaults

Если пользователь выбрал участника семьи в smart field:

- по умолчанию `memberAccountIds = [selectedMemberId]`

Но это должно происходить только как initial default.

Если пользователь потом вручную поменял уведомления:

- дальнейшие смены title не должны автоматически перетирать recipients

### 4. Recipients remain editable

Блок `Кому приходят уведомления` остаётся отдельным:

- можно выбрать одного или нескольких получателей
- можно убрать выбранного адресата плана
- можно назначить другого получателя push

Таким образом:

- `для кого план` отвечает за смысл и заголовок
- `кому приходят уведомления` отвечает за доставку push

## Scope

Первый этап только фронтенд:

- новый UX на setup screen
- новый sheet для выбора адресата плана
- локальная draft-логика
- автогенерация title
- правила дефолтной автоподстановки recipients

Без backend-изменений:

- API payload остаётся прежним
- в backend по-прежнему уходит `title`
- в backend по-прежнему уходит `memberAccountIds`

## Frontend Implementation Plan

### 1. Extend draft state

Файл:

- `frontend/src/client/pages/pillbox/shared.tsx`

Добавить в `SetupDraft`:

- `targetMemberId: string | null`
- флаг режима title, например:
  - `titleSource: "member" | "manual"`
- флаг ручной правки recipients, например:
  - `recipientsCustomized: boolean`

Цель:

- различать автогенерированный title и ручной title
- понимать, можно ли ещё автоподставлять recipients

### 2. Keep API payload unchanged

Файл:

- `frontend/src/shared/api/pillboxPlans.contract.ts`

Ничего не менять в API contract на первом этапе.

`targetMemberId` живёт только во frontend draft-state и используется для UX-логики.

### 3. Add title generation helper

Файлы:

- `frontend/src/client/pages/pillbox/shared.tsx`
- или отдельный util рядом с pillbox

Добавить helper:

- принимает member data
- возвращает автозаголовок по правилам `роль + имя`

### 4. Add target member sheet

Новый компонент рядом с pillbox screen components.

Примерное назначение:

- открыть список семейных участников
- дать выбрать одного участника
- дать fallback `Ввести вручную`

Sheet должен переиспользовать уже существующий mobile pattern:

- bottom sheet
- selectable rows
- визуально близко к `PlanPushRecipientsField`

### 5. Replace plain title input in setup screen

Файл:

- `frontend/src/client/pages/pillbox/setupScreen.tsx`

Переделать секцию названия:

- вместо обычного input сделать smart field / selector row
- по tap открывать новый sheet
- в manual mode показывать обычный input для ручного редактирования

### 6. Update setup logic in PillboxPage

Файл:

- `frontend/src/client/pages/PillboxPage.tsx`

Нужно добавить правила:

- при выборе участника:
  - сохранять `targetMemberId`
  - генерировать title
  - проставлять recipients по умолчанию
- при ручном редактировании title:
  - переключать draft в `manual`
- при ручном редактировании recipients:
  - ставить `recipientsCustomized = true`
- после этого не перетирать recipients автоматически

### 7. Preserve existing recipients editor

Файл:

- `frontend/src/client/pages/pillbox/PlanPushRecipientsField.tsx`

Оставить текущий editor уведомлений:

- как отдельную настройку
- без скрытой связи с title после ручной правки

### 8. Optional display improvements in details/hub

Файлы:

- `frontend/src/client/pages/pillbox/detailsScreen.tsx`
- `frontend/src/client/pages/pillbox/hubScreen.tsx`

Если title автогенерируется по новым правилам, проверить:

- как он выглядит в карточках
- не слишком ли длинные склейки
- достаточно ли `truncate` на мобильном

Это может не требовать логических правок, только визуальную валидацию.

## Suggested Screen Behavior

### Happy path

1. Пользователь открывает создание плана
2. Тапает по полю названия
3. В sheet выбирает участника семьи
4. Поле получает title вроде `Для няни Инны`
5. Уведомления автоматически ставятся на этого участника
6. Пользователь добавляет лекарства
7. При необходимости открывает `Кому приходят уведомления` и меняет recipients
8. Сохраняет план

### Manual naming path

1. Пользователь открывает создание плана
2. Тапает по полю названия
3. Выбирает `Ввести вручную`
4. Вводит собственное название
5. Сам выбирает получателей уведомлений
6. Сохраняет план

## Tests

Добавить frontend tests на:

- генерацию title из `role + name`
- выбор участника семьи как источника title
- автопроставление одного default recipient
- прекращение автоподстановки после ручной смены recipients
- сохранение manual title без перезаписи

Примерные зоны:

- `frontend/test/recipientSelection.test.ts`
- новый тест рядом с pillbox logic

## Out of Scope

В первый этап не входят:

- backend migration
- новое поле `targetMemberId` в API
- аналитика по адресату плана
- смена contract списка/деталей pillbox plan

Это можно рассмотреть позже, если продукт захочет сделать `для кого план` отдельной доменной сущностью.

## Final Recommendation

Лучший первый шаг:

- не пытаться объяснять текущую двусмысленность текстом
- не оставлять свободный title как основной сценарий
- не смешивать адресата плана и recipients в одно поле

Нужно:

- превратить `Название плана` в smart field
- дать выбор участника семьи или ручной ввод
- автогенерировать title из `роль + имя`
- проставлять recipients по умолчанию на выбранного участника
- оставить recipients отдельной настраиваемой секцией

Это решает путаницу, сохраняет гибкость и укладывается в фронтенд-only этап.
