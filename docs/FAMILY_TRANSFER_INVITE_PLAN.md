# Family Transfer On Invite Plan

> Status: superseded / not current.
>
> Этот документ описывает старую идею destructive transfer-flow при вступлении в другую семью по invite.
> Текущая рабочая логика проекта другая:
> - `remove member` сохраняет аккаунт;
> - участнику создаётся новая пустая семья;
> - invite-join остаётся консервативным и не переводит аккаунт из непустой семьи автоматически.
>
> Документ оставлен как исторический product note, а не как активный roadmap.

План доработки сценария, когда аккаунт пытается вступить в другую семью по invite, но в его текущей solo-family уже есть данные.

## 1. Problem

Сейчас `accept_family_invite()` разрешён только для пустой solo-family.

Backend блокирует переход, если в текущей семье есть:
- другие участники;
- дети;
- домашняя аптечка;
- записи родителей.

Причина в том, что ключевые данные живут на `family_id`, а не на `account_id`. Простой перевод аккаунта в другую семью без отдельного destructive flow приведёт к неочевидной потере доступа к прежним данным.

## 2. Product Goal

Поддержать осознанный переход в другую семью по invite даже для аккаунта, у которого уже есть собственные данные, но сделать это:
- явно;
- безопасно;
- без скрытого изменения текущей логики пустой семьи;
- без молчаливой потери данных.

## 3. Recommended Approach

### 3.1 Keep current fast path

Если текущая family фактически пустая, join-flow работает как сейчас:
- preview invite;
- accept invite;
- перенос аккаунта в новую семью;
- удаление старой пустой solo-family.

### 3.2 Add explicit destructive path

Если в текущей семье есть данные, backend не должен возвращать только общую ошибку. Вместо этого нужен отдельный подтверждаемый сценарий:
- показать, какие данные есть в текущей семье;
- предложить сохранить их;
- дать явный destructive action;
- выполнить join только после отдельного подтверждения.

## 4. Why not “archive silently in DB”

Вариант “отвязать аккаунт и скрыто архивировать старую семью” сейчас не рекомендован.

Причины:
- в модели нет отдельной сущности archived family;
- непонятно, кто владеет архивом после перехода;
- потребуется новая логика исключения архивов из обычных выборок, billing, push, лимитов и аналитики;
- появится скрытое состояние, которое пользователь не видит и не понимает, как восстановить.

Это можно делать только как отдельную большую продуктовую фичу, а не как быстрый фикс invite-flow.

## 5. Scope Of The New Flow

### 5.1 Trigger condition

Новый flow нужен, если аккаунт вступает в другую семью, а в его текущей семье есть хотя бы одно из:
- дети;
- записи аптечки;
- pillbox-планы;
- профили родителей;
- другие семейные данные, которые реально пропадут из доступа после перехода.

### 5.2 User promise

Нужно формулировать честно:

`При переходе в другую семью ваши текущие семейные данные останутся в прежней семье и будут недоступны из нового семейного кабинета.`

Если мы выбираем destructive cleanup вместо сохранения старой семьи, текст должен быть ещё жёстче:

`При переходе в другую семью текущая семья и её данные будут удалены.`

Финальный текст зависит от того, удаляем ли мы старую family физически или только даём потерять к ней доступ.

## 6. Export Requirement Before Destructive Join

Перед destructive переходом пользователю нужен способ сохранить свои данные.

### 6.1 Minimum export goal

Дать пользователю скачать архив перед переходом в другую семью.

Минимально в архив должны входить:
- дети;
- история болезней и события;
- измерения, сон, кормление;
- домашняя аптечка;
- pillbox-планы и история приёмов;
- метаданные семьи и участников.

### 6.2 Format

Рекомендуемый формат:
- один `zip` архив;
- внутри человекочитаемые файлы `xlsx/csv`;
- параллельно machine-readable `json`, если в будущем появится import.

Пример структуры:

```text
family-export.zip
  family.json
  members.json
  children/
    child-1.xlsx
    child-1.json
    child-2.xlsx
    child-2.json
  cabinet.xlsx
  cabinet.json
  pillbox.xlsx
  pillbox.json
```

### 6.3 Existing base

В проекте уже есть child export. Его можно использовать как основу, но этого недостаточно:
- сейчас нет единого family-level export;
- нет export аптечки;
- нет export pillbox;
- нет объединяющего архива перед join/leave сценариями.

## 7. UX Flow

### 7.1 Current empty-family flow

1. Пользователь открывает invite.
2. Нажимает `Присоединиться к семье`.
3. Join проходит как сейчас.

### 7.2 New non-empty-family flow

1. Пользователь открывает invite.
2. Нажимает `Присоединиться к семье`.
3. Backend возвращает не generic error, а structured response о том, что текущая семья содержит данные.
4. UI открывает confirm-state.
5. На confirm-state показываются counts:
   - `2 ребёнка`
   - `14 препаратов в аптечке`
   - `3 плана таблетницы`
6. Пользователь видит действия:
   - `Скачать архив данных`
   - `Остаться в текущей семье`
   - `Перейти и удалить текущую семью`
7. Только после отдельного подтверждения запускается destructive join.

### 7.3 UI notes

Важно:
- не прятать destructive action рядом с обычной primary CTA;
- не использовать для этого обычный success-style button без warning контекста;
- держать copy предельно конкретным, без эвфемизмов.

## 8. Backend Plan

### 8.1 Add current family transfer preview

Нужен отдельный backend preview для join-transition.

Назначение:
- проверить, пустая ли текущая семья;
- вернуть counts по данным;
- вернуть флаг, требуется ли destructive confirmation.

Пример структуры ответа:

```json
{
  "requires_confirmation": true,
  "current_family_name": "Моя семья",
  "summary": {
    "children_count": 2,
    "cabinet_items_count": 14,
    "pillbox_plans_count": 3,
    "parent_profiles_count": 1
  }
}
```

### 8.2 Keep accept path unchanged for safe scenario

Текущий `accept_family_invite()` нужно сохранить как safe path для пустой семьи.

### 8.3 Add explicit force accept path

Нужен отдельный сценарий, например:
- `force_accept_family_invite(token)`
- или `accept_family_invite(..., force=true)` только если API и audit останутся предельно явными.

Предпочтительнее отдельный endpoint/handler, чтобы destructive path не смешивался с обычным accept.

### 8.4 Define data handling explicitly

До реализации force path нужно выбрать один из двух backend-вариантов:

1. `Delete old family data`
- после подтверждения удаляем прежнюю family и связанные данные;
- проще логически;
- жёсткий destructive сценарий.

2. `Leave old family disconnected`
- аккаунт уходит в новую family;
- старая family и данные остаются в БД без активного аккаунта;
- это создаёт orphaned state и требует отдельной политики уборки/восстановления.

Для первой версии рекомендуется `Delete old family data`, потому что это честнее и проще поддерживать.

### 8.5 Add audit trail

Нужен явный audit/event log:
- кто выполнил destructive join;
- из какой family ушёл;
- в какую family вступил;
- был ли скачан export перед этим.

## 9. Frontend Plan

### 9.1 JoinFamilyPage

На `JoinFamilyPage` нужен новый confirm-state:
- загрузка preview текущей семьи;
- список counts;
- warning copy;
- кнопки `Скачать архив данных`, `Остаться`, `Перейти и удалить`.

### 9.2 Error handling

Нельзя оставлять это как обычный toast или общий backend detail.

Нужен typed API response / typed error code, чтобы UI мог перейти в отдельное состояние подтверждения.

### 9.3 Export UX

Экспорт должен запускаться прямо из confirm-flow:
- без похода по разным разделам app;
- без требования вручную искать экспорт ребёнка;
- с понятным success-state после скачивания.

## 10. Rollout Order

Рекомендуемый порядок:

1. Описать точную бизнес-политику:
   - удаляем ли старую family физически;
   - обязателен ли export или он optional.
2. Сделать backend preview текущих данных.
3. Сделать frontend confirm-state на invite join.
4. Сделать family export archive.
5. Сделать отдельный destructive accept endpoint.
6. Добавить audit trail и регрессионные тесты.
7. Прогнать ручные сценарии в dev и затем короткий smoke в production.

## 11. Manual Test Matrix

Нужно покрыть:

1. Пустая solo-family -> join проходит без confirm-flow.
2. Solo-family с детьми -> появляется destructive confirm-flow.
3. Solo-family с аптечкой, но без детей -> тоже появляется confirm-flow.
4. Solo-family с pillbox history -> появляется confirm-flow.
5. Export доступен и скачивается до destructive join.
6. `Остаться в текущей семье` ничего не меняет.
7. `Перейти и удалить текущую семью` завершает переход и очищает старый контейнер согласно выбранной политике.
8. Аккаунт с активным billing ownership context всё ещё блокируется отдельно.
9. Owner целевой семьи и existing members не теряют данные в принимающей семье.

## 12. Recommendation

Для первой реализации рекомендуется:
- не вводить скрытый DB archive;
- не менять молча текущий `accept_family_invite`;
- делать отдельный explicit destructive flow;
- перед destructive join дать понятный export данных.

Это самый безопасный вариант по продукту, UX и сопровождению.
